# Codex Beginner Bridge — Product Scope

## 1. 문서 목적

이 문서는 Codex Beginner Bridge의 제품 방향과 V0.1 범위를 정의하는 제품 기준 문서다.

공식 상태 체계의 정의는 BEGINNER_REPORT_SPEC.md를 SSOT(Single Source of Truth)로 사용한다. 
본 문서에서 동일한 표현이 예시로 등장하더라도 상태 체계의 정의를 변경하지 않는다.

이 문서는 다음 질문에 답한다.

* 이 프로젝트는 누구를 위한 것인가
* 어떤 문제를 해결하는가
* V0.1에서 무엇을 제공하는가
* V0.1에서 무엇을 제공하지 않는가
* 제품이 따라야 할 핵심 원칙은 무엇인가
* V0.1이 성공했다고 판단하는 기준은 무엇인가

구체적인 보고서 작성 형식, 용어 설명 규칙, 위험도 판단 기준, Skill 실행 절차는 별도 문서에서 정의한다.

이 문서는 시스템 지침이나 Codex의 상위 지침을 무시하지 않는다.

이 프로젝트 내부 문서 사이에서 제품 방향이 충돌할 경우, 승인된 결정 기록이 없다면 이 문서를 제품 범위 판단의 기준으로 사용한다.

---

## 2. 프로젝트 한 줄 정의

Codex Beginner Bridge는 Codex가 작업 후 확인한 사실, 예상되는 변화, 확인하지 못한 내용을 구분하여 비개발자가 이해할 수 있는 짧고 명확한 하나의 보고서로 제공하는 오픈소스 Codex Skill이다.

---

## 3. 해결하려는 문제

비개발자는 Codex를 사용해 프로그램을 만들 수 있지만, Codex가 어떤 작업을 했는지 정확하게 이해하기 어렵다.

### 3.1 어려운 개발 용어

Codex는 다음과 같은 개발 용어를 사용할 수 있다.

* API
* GUI
* IDE
* Component
* Route
* Middleware
* Refactoring
* Dependency
* Runtime
* Build
* Deploy

비개발자는 단어를 읽을 수 있어도 해당 용어가 현재 프로젝트에서 어떤 역할을 하는지 이해하기 어려울 수 있다.

Codex Beginner Bridge는 필요한 개발 용어가 처음 등장할 때 원래 용어와 쉬운 설명을 함께 제공한다.

예시:

* API(프로그램끼리 정보를 주고받는 연결 통로)
* GUI(사용자가 눈으로 보고 조작하는 프로그램 화면)
* IDE(코드를 작성하고 실행하는 작업 공간)
* Component(화면을 구성하는 재사용 가능한 조각)

### 3.2 변경 내용 확인의 어려움

Codex는 하나의 요청을 처리하면서 여러 파일을 수정할 수 있다.

비개발자는 다음 내용을 구분하기 어렵다.

* 무엇이 변경됐는가
* 사용자가 보는 화면이 달라졌는가
* 프로그램 내부 동작이 달라졌는가
* 어떤 파일이 주요하게 수정됐는가
* 기존 기능에 영향을 줄 가능성이 있는가
* 실제로 어떤 검증을 실행했는가
* 실행하지 못한 검증은 무엇인가

Git diff가 제공되더라도 코드 문법을 모르면 변경의 의미를 이해하기 어렵다.

### 3.3 사실과 예상의 구분 어려움

Codex가 코드를 읽고 예상한 결과와 실제 실행으로 확인한 결과가 같은 문장 안에 섞일 수 있다.

예를 들어 Codex가 화면을 직접 실행하지 않았는데도 다음과 같이 표현할 수 있다.

> 버튼이 정상적으로 표시됩니다.

실제로 화면을 확인하지 않았다면 다음처럼 표현해야 한다.

> 코드상 버튼이 표시될 것으로 예상됩니다. 실제 화면은 확인하지 못했습니다.

Codex Beginner Bridge는 확인 상태를 명확하게 구분한다.

### 3.4 다음 행동 판단의 어려움

비개발자는 작업 보고를 읽은 뒤에도 다음 행동을 결정하기 어렵다.

* 바로 승인해도 되는가
* 직접 화면을 확인해야 하는가
* 추가 테스트를 요청해야 하는가
* 작업을 보류해야 하는가
* 어떤 기능을 우선 확인해야 하는가

Codex Beginner Bridge는 사용자가 판단할 수 있도록 검증 상태와 확인 항목을 제공한다.

최종 승인이나 배포 결정은 사용자가 한다.

## 4. 목표 사용자

### 4.1 주요 사용자

다음 조건에 해당하는 사용자를 주요 대상으로 한다.

* Codex로 웹사이트나 프로그램을 만드는 사람
* 개발자가 아니거나 개발 지식이 많지 않은 사람
* 자연어로 Codex에게 작업을 요청하는 사람
* Codex의 작업 결과를 이해하고 승인해야 하는 사람
* 작은 개인 프로젝트나 초기 제품을 운영하는 사람
* AI를 이용해 바이브 코딩을 하는 사람

### 4.2 보조 사용자

다음 사용자도 활용할 수 있다.

* 입문 개발자
* 서비스 기획자
* 디자이너
* 소규모 팀의 프로젝트 관리자
* 개발 결과를 쉽게 설명해야 하는 개발자
* Codex를 교육에 활용하는 강사와 학습자

### 4.3 초기 범위에서 제외되는 사용자

다음 사용자를 위한 전문 기능은 V0.1의 주요 범위가 아니다.

* 대규모 기업 개발 조직
* 전문 보안 감사 담당자
* 전문 코드 리뷰어
* 복잡한 모노레포 운영팀
* 규제 산업의 공식 검증 담당자
* Codex 이외의 코딩 에이전트만 사용하는 사람

## 5. V0.1 핵심 목표

V0.1의 목표는 다음과 같다.

> Codex가 작업을 완료한 뒤 비개발자가 별도의 추가 질문 없이 무엇이 바뀌었고, 무엇이 실제로 확인됐으며, 무엇을 직접 확인해야 하는지 이해할 수 있게 한다.

V0.1은 완성된 시각 프로그램이 아니다.

V0.1은 다음 요소로 구성되는 지침 기반 검증 버전이다.

* `AGENTS.md`
* Codex Skill
* 보고서 작성 기준
* 용어 설명 기준
* 위험도 판단 기준
* 검증 시나리오

## 6. V0.1 핵심 기능

### 6.1 하나의 비개발자용 최종 보고

기술 보고서와 비개발자용 보고서를 따로 생성하지 않는다.

Codex의 하나의 최종 답변 자체가 비개발자가 이해할 수 있는 형태여야 한다.

보고서는 작업 규모에 맞게 길이를 조절한다.

단순한 작업에 불필요하게 긴 보고서를 생성하지 않는다.

### 6.2 필수 보고 항목

모든 코드 변경 작업의 최종 보고에는 다음 6개 항목을 기본으로 포함한다.

1. 변경 요약
2. 사용자 화면에서 예상되거나 확인된 변화
3. 프로그램 내부 기능의 변화
4. 주요 수정 파일
5. 실행한 검증과 실행하지 못한 검증
6. 위험 요소와 사용자가 직접 확인할 항목

해당하지 않는 항목은 한 문장으로 짧게 표시하거나 생략할 수 있다.

예시:

> 사용자 화면 변화: 없음

### 설치와 로컬 운영 지원

보고서 생성 경로는 Codex Skill을 기본으로 유지한다. V0.1에서는 사용자가 Skill을 수동 복사하지 않도록 다음 로컬 보조 기능을 제공할 수 있다.

* 프로젝트 또는 사용자 전역 범위의 Distribution CLI
* 개인 베타 설정을 관리하는 로컬 관리자 화면
* Skill 규칙을 읽기 전용으로 제공하는 선택형 로컬 MCP

이 기능들은 127.0.0.1 또는 로컬 프로세스에서만 동작한다. 중앙 서버, 원격 Telemetry, 사용자 계정, 공개 웹 대시보드와는 연결하지 않는다. MCP 서버 실행과 실제 Codex 도구 호출은 별도 상태로 취급한다.

### 6.3 조건부 보고 항목

다음 항목은 작업이 복잡하거나 관련 정보가 있을 때만 추가한다.

* 새로 생성된 파일
* 삭제된 파일
* 데이터 저장 방식 변경
* 설정 또는 환경변수 변경
* 외부 서비스 변경
* 보안 관련 변경
* 배포 관련 주의사항
* 기존 변경과 이번 작업의 구분
* 주요 파일 이외의 전체 변경 파일 목록

### 6.4 보고 정보 체계

V0.1의 보고 정보는 다음 네 가지 체계로 구분한다.

#### 근거 출처

Codex가 무엇을 바탕으로 판단했는지를 나타낸다.

* 파일
* Git
* 명령
* 브라우저 또는 실제 실행
* 코드 예상
* 사용자 제공 정보

#### 확인 상태

해당 내용이 어느 정도 확인됐는지를 나타낸다.

* 확인됨
* 일부 확인
* 확인하지 못함

#### 사용자 행동

사용자가 직접 해야 할 일을 나타낸다.

* 사용자 확인 필요
* 추가 테스트 권장
* 설정 필요
* 사용자 결정 필요

#### 보고서 상태

현재 작업 전체의 상태를 나타낸다.

* 확인 완료
* 추가 확인 필요
* 일부 확인
* 작업 보류
* 범위 밖

근거 출처, 확인 상태, 사용자 행동, 보고서 상태를 같은 의미로 사용하지 않는다.

구체적인 적용 기준은 `docs/BEGINNER_REPORT_SPEC.md`에서 정의한다.

### 6.5 주요 수정 파일 설명

모든 변경 파일을 같은 비중으로 설명하지 않는다.

사용자 기능에 직접 영향을 주는 주요 파일만 역할을 설명한다.

기본적으로 최대 5개의 주요 파일을 설명한다.

변경 파일이 5개보다 많다면 다음과 같이 처리한다.

* 주요 파일 최대 5개: 역할과 변경 이유를 설명
* 나머지 파일: 경로 목록 또는 개수만 표시
* 생성 파일이나 설정 파일: 필요할 때 별도 표시

예시:

> 주요 파일
> `src/features/auth/LoginForm.tsx`
> 로그인 화면의 입력창과 버튼을 구성하는 파일입니다.

> 그 외 변경 파일
> 스타일 파일 3개와 테스트 파일 2개가 함께 수정됐습니다.

### 6.6 개발 용어 설명

다음 조건에 해당하는 용어만 쉬운 설명을 제공한다.

* 사용자가 작업 결과를 이해하는 데 필요한 용어
* 일반 사용자가 의미를 모를 가능성이 높은 용어
* 위험이나 검증 결과를 판단하는 데 필요한 용어

같은 보고서에서 동일한 용어를 반복 설명하지 않는다.

프로젝트와 무관한 일반 개발 지식을 길게 설명하지 않는다.

기술적 의미를 왜곡할 정도로 지나치게 단순화하지 않는다.

### 6.7 위험도 안내

위험도는 다음 기준을 사용한다.

#### 낮음

다음과 같이 프로그램 핵심 동작에 영향을 줄 가능성이 작은 변경이다.

* 문구
* 색상
* 여백
* 화면 배치
* 문서
* 주석
* 테스트 설명

#### 중간

특정 기능의 동작이나 사용자 흐름에 영향을 줄 수 있는 변경이다.

* 버튼 동작
* 화면 이동
* 폼 검증
* 특정 기능의 상태 처리
* 특정 페이지의 데이터 표시
* 파일 업로드
* 로컬 저장 방식

#### 높음

여러 기능이나 중요한 데이터에 영향을 줄 수 있는 변경이다.

* 로그인과 인증
* 사용자 권한
* 결제
* 데이터베이스 구조
* 공통 상태 관리
* 공통 API 처리
* 외부 서비스 연결
* 비밀정보 처리
* 배포 설정
* 여러 페이지가 사용하는 공통 기능

#### 판정 불가

변경 범위나 실행 환경을 충분히 확인하지 못해 위험도를 판단할 수 없는 상태다.

위험도에는 반드시 짧은 근거를 함께 작성한다.

위험도는 정상 작동 여부를 의미하지 않는다.

낮은 위험도라고 해서 테스트가 필요 없는 것은 아니다.

### 6.8 보고서 상태

최종 보고서 상태는 다음 중 하나를 사용한다.

* 확인 완료
* 추가 확인 필요
* 일부 확인
* 작업 보류
* 범위 밖

각 상태를 결정하는 구체적인 조건과 우선순위는 `docs/BEGINNER_REPORT_SPEC.md`에서 정의한다.

보고서 상태는 사용자의 승인이나 배포 결정을 대신하지 않는다.

## 7. 핵심 제품 원칙

### 7.1 요약 우선 원칙

보고서 앞부분에는 비개발자가 먼저 알아야 할 정보를 배치한다.

순서는 다음을 우선한다.

1. 무엇이 바뀌었는가
2. 화면이나 사용 방법이 어떻게 달라지는가
3. 무엇이 실제로 확인됐는가
4. 무엇을 직접 확인해야 하는가

파일 경로와 기술 세부사항은 그다음에 배치한다.

### 7.2 사실과 예상 분리 원칙

실제로 확인한 내용과 코드만 보고 예상한 내용을 같은 표현으로 작성하지 않는다.

* 실행한 결과는 `확인됨` 또는 `실행 결과로 확인됨`
* 코드만 보고 판단한 결과는 `예상됨`
* 실행할 수 없는 결과는 `확인하지 못함`
* 사용자가 직접 볼 내용은 `사용자 확인 필요`

확인하지 않은 결과를 정상 작동한다고 표현하지 않는다.

### 7.3 화면 변화와 내부 변화 구분 원칙

사용자가 직접 보는 변화와 프로그램 내부의 변화를 구분한다.

예시:

> 사용자 화면의 변화
> 로그인 버튼 아래에 비밀번호 찾기 링크가 표시될 것으로 예상됩니다.

> 내부 기능의 변화
> 비밀번호 찾기 페이지로 이동하는 경로가 추가됐습니다.

화면을 실제로 실행하지 않았다면 `표시됩니다`가 아니라 `표시될 것으로 예상됩니다`라고 작성한다.

### 7.4 기능 중심 설명 원칙

비개발자에게 폴더와 코드 구조만 나열하지 않는다.

가능한 경우 다음처럼 기능 단위로 설명한다.

* 로그인
* 회원가입
* 검색
* 장바구니
* 결제
* 관리자 화면
* 알림
* 파일 업로드

파일은 해당 기능과 함께 설명한다.

### 7.5 최소 변경 원칙

최소 변경은 다음을 의미한다.

* 사용자가 요청한 기능과 직접 관련된 범위만 수정
* 기존 구조를 불필요하게 다시 작성하지 않음
* 요청하지 않은 리팩터링을 함께 진행하지 않음
* 디자인 요청 때문에 데이터베이스나 API를 수정하지 않음
* 필요한 경우에만 공통 파일을 수정

Codex는 작업 범위가 명확하지 않으면 추측으로 범위를 크게 확대하지 않는다.

### 7.6 기존 변경 보호 원칙

작업 시작 전부터 존재한 변경과 이번 작업으로 발생한 변경을 가능한 범위에서 구분한다.

상태는 다음처럼 표시한다.

* 작업 시작 전부터 있던 변경
* 이번 작업으로 발생한 변경
* 어느 작업에서 발생했는지 판단하기 어려운 변경

기존 변경을 임의로 삭제하거나 되돌리지 않는다.

### 7.7 검증 가능성 원칙

Git, 테스트 명령, 빌드 도구, 브라우저 또는 변경 내용이나 영향 범위를 충분히 확인할 수 없는 경우에만 위험도를 판정 불가로 표시한다.

실행하지 못한 검증을 통과했다고 표현하지 않는다.

테스트 명령이 없는 프로젝트에서는 다음처럼 작성한다.

> 확인하지 못함: 프로젝트에 확인 가능한 자동 테스트 명령이 없습니다.

Git이 없는 프로젝트에서는 다음처럼 작성한다.

> 확인하지 못함: Git 기록이 없어 이번 작업의 변경 파일을 자동으로 구분하지 못했습니다.

검증 가능성과 위험도는 별도로 판단한다.

테스트, 브라우저 또는 실행 환경이 없더라도 코드와 변경 범위를 확인할 수 있다면 위험도를 판단할 수 있다.

반대로 코드나 변경 범위 자체를 확인하지 못한 경우에는 위험도를 `판정 불가`로 표시할 수 있다.


### 7.8 비밀정보 보호 원칙

보고서에 다음 값을 직접 노출하지 않는다.

* API 키
* 비밀번호
* 접근 토큰
* 세션 값
* 인증 쿠키
* 개인 식별 정보
* 환경변수의 실제 비밀 값

필요한 경우 변수 이름만 표시한다.

예시:

> `WEATHER_API_KEY` 환경변수가 필요합니다. 실제 값은 보고서에 표시하지 않았습니다.

### 7.9 낮은 운영 비용 원칙

V0.1은 중앙 서버와 별도 AI API 없이 작동해야 한다.

사용자가 이미 사용하는 Codex 환경과 프로젝트 내부 지침을 활용한다.

V0.1에서는 다음을 우선한다.

* Markdown 문서
* Codex Skill
* 로컬 프로젝트
* Codex가 직접 확인할 수 있는 파일과 명령

## 8. Skill 작동 범위

### 8.1 코드 변경 작업 완료 후

Codex가 파일을 생성, 수정 또는 삭제한 뒤 최종 작업 보고를 작성할 때 작동한다.

### 8.2 보고서만 요청한 경우

사용자가 현재 변경 내용을 쉬운 말로 설명해달라고 요청하면 작동한다.

이 경우 프로젝트 코드를 수정하지 않는다.

### 8.3 코드 설명만 요청한 경우

사용자가 특정 파일이나 코드 블록의 역할을 설명해달라고 요청하면 비개발자 눈높이로 설명한다.

이 경우 전체 작업 완료 보고서를 강제로 생성하지 않는다.

### 8.4 계획만 요청한 경우

사용자가 구현 전에 계획을 요청하면 완료 보고서가 아니라 다음 내용을 제공한다.

* 무엇을 바꿀 예정인지
* 어떤 기능이 영향을 받을 수 있는지
* 어떤 파일을 확인할 예정인지
* 어떤 검증이 필요할지

실제로 변경하지 않은 내용을 완료된 것처럼 작성하지 않는다.

### 8.5 일반 질문

단순한 개발 개념 질문이나 프로젝트와 무관한 질문에는 긴 작업 보고서 형식을 적용하지 않는다.

### 8.6 사용자가 상세 보고를 원하지 않는 경우

사용자가 “코드만 수정해주세요”, “보고서는 생략해주세요”처럼 상세 보고를 원하지 않는다고 명시한 경우 기본 6개 항목을 모두 출력하지 않아도 된다.

대신 다음 최소 정보는 짧게 제공한다.

* 작업 완료 여부
* 주요 수정 파일
* 중요한 실패 또는 확인하지 못한 항목

안전 문제, 데이터 손실 가능성, 비밀정보 노출 또는 핵심 검증 실패는 사용자가 보고서 생략을 요청했더라도 숨기지 않는다.

요청 예시:

* 불필요하게 긴 보고서를 생성하지 않는가

확인 항목:

* 화면 변화와 입력 검증 기능 변화를 구분하는가
* 사용자가 이해하기 어려운 용어를 필요한 범위에서 설명하는가
* 특정 기능만 수정됐는지 설명하는가
* 관련 테스트 실행 여부를 명시하는가
* 기존 검색 기능에 미칠 수 있는 영향을 설명하는가
* 위험도와 근거를 일관되게 작성하는가

## 11. 성공 기준

### 11.1 이해 가능성 평가

비개발자 평가자는 보고서를 읽고 다음 7개 질문에 답한다.

1. 무엇이 바뀌었는가
2. 화면이나 사용 방법이 어떻게 달라지는가
3. 프로그램 내부에서 무엇이 달라졌는가
4. 무엇이 실제로 확인됐는가
5. 무엇이 아직 확인되지 않았는가
6. 무엇을 직접 확인해야 하는가
7. 추가 확인이 필요한 상태인가

7개 중 6개 이상에 추가 질문 없이 답할 수 있어야 한다.

### 11.2 사실 정확성

다음 정보가 실제 프로젝트 상태와 일치해야 한다.

* 주요 수정 파일
* 생성 또는 삭제된 파일
* 실행한 명령
* 테스트 결과
* 확인하지 못한 항목

### 11.3 표현 정확성

다음 조건을 만족해야 한다.

* 실제 확인과 예상을 구분한다.
* 실행하지 않은 테스트를 통과했다고 쓰지 않는다.
* 화면을 실행하지 않았다면 실제 화면 결과를 보장하지 않는다.
* 비밀정보를 노출하지 않는다.
* 사용자 승인과 정상 작동 여부를 동일하게 취급하지 않는다.

### 11.4 길이 적절성

단순 화면 변경 보고서는 핵심 내용을 우선하고 반복 설명을 피해야 한다.

기본 보고서는 가능한 한 짧게 작성하며, 상세 기술 정보는 필요한 경우에만 추가한다.

고정된 글자 수를 강제하지 않지만 다음 기준을 사용한다.

* 단순 작업: 짧은 요약 중심
* 중간 규모 작업: 주요 기능과 검증 중심
* 복잡하거나 위험한 작업: 필요한 세부정보 추가

### 11.5 재사용성

동일한 Skill을 서로 다른 Codex 프로젝트에 적용해도 다음 규칙이 유지돼야 한다.

* 하나의 최종 보고
* 사실과 예상의 구분
* 주요 파일 중심 설명
* 실행 및 미실행 검증 구분
* 사용자 확인 항목 제공

## 12. V0.1 완료 조건

다음 조건을 모두 만족하면 V0.1 제품 범위가 검증된 것으로 판단한다.

* 주요 수정 파일의 역할이 설명됐다.
* 실행한 검증과 실행하지 못한 검증이 구분됐다.
* 화면을 실행하지 않은 경우 예상 표현을 사용했다.
* 위험도에 근거가 포함됐다.
* 사용자가 직접 확인할 항목이 제공됐다.
* 비밀정보가 노출되지 않았다.
* 비개발자 평가 질문 7개 중 6개 이상에 답할 수 있었다.
* 보고서가 작업 규모에 비해 지나치게 길거나 반복적이지 않았다.
* docs/TEST_SCENARIOS.md가 준비되지 않았다면 비개발자 이해 평가는 완료로 판단하지 않는다.

## 14. 변경 관리

이 문서의 제품 범위를 변경할 때는 다음 절차를 따른다.

1. 변경하려는 내용을 설명한다.
2. 변경 이유를 작성한다.
3. 기존 범위와 충돌하는 항목을 확인한다.
4. V0.1에 포함할지 이후 버전으로 이동할지 결정한다.
5. `docs/DECISIONS.md`에 결정 내용을 기록한다.
6. 관련 문서를 함께 수정한다.
7. 사용자 승인 후 적용한다.

Codex는 사용자 승인 없이 이 문서의 제품 방향을 임의로 확대하지 않는다.

이 규칙은 제품 범위 문서를 수정할 때 적용한다.

일반적인 코드 구현 작업 전체를 금지하는 규칙이 아니다.

* 대상 사용자: 비개발자 및 입문 사용자
* 초기 제공 방식: `AGENTS.md`와 Codex Skill, 선택형 로컬 MCP 및 Distribution CLI
* 초기 실행 환경: 로컬 프로젝트
* 별도 AI API: 사용하지 않음
* 중앙 서버: 사용하지 않음
* 초기 출력 형식: Codex의 하나의 최종 답변
* 기본 보고 항목: 6개
* 주요 파일 설명 한도: 기본 최대 5개
* 위험도: 낮음 / 중간 / 높음 / 판정 불가
* 보고서 상태: 확인 완료 / 추가 확인 필요 / 일부 확인 / 작업 보류 / 범위 밖
* 필수 검증 시나리오: 단순 화면 변경 1개
* 보조 검증 시나리오: 내부 기능 변경 1개
* 외부 API 검증: V0.1 범위 밖
* HTML 보고서: V0.3 이후
* MCP: V0.1 선택형 로컬 읽기 연결, 중앙·쓰기 확장은 이후 검토
* Claude Code 지원: Codex 버전 검증 이후 검토
* 오픈소스 공개 목표: V1
* 근거 출처:

  * 파일
  * Git
  * 명령
  * 브라우저 또는 실제 실행
  * 코드 예상
  * 사용자 제공 정보
* 확인 상태:

  * 확인됨
  * 일부 확인
  * 확인하지 못함
* 사용자 행동:

  * 사용자 확인 필요
  * 추가 테스트 권장
  * 설정 필요
  * 사용자 결정 필요
* 보고서 상태:

  * 확인 완료
  * 추가 확인 필요
  * 일부 확인
  * 작업 보류
  * 범위 밖
* 상세 보고 생략 요청: 최소 보고 허용
* 위험도와 검증 가능성: 별도 판단
