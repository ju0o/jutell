# JuTell — Glossary Policy

## 1. 목적과 적용 범위

이 문서는 AI Agent 작업 보고서에서 개발 용어를 비개발자에게 설명하는 기본 정책을 정의한다.

제품 범위는 `docs/PRODUCT_SCOPE.md`, 보고서 상태와 보고서 작성 규칙은 `docs/BEGINNER_REPORT_SPEC.md`가 기준이다. 긴 용어 목록과 상세 예시는 다음 reference 문서에서 관리한다.

`.agents/skills/beginner-bridge/references/glossary-ko.md`

## 2. 기본 원칙

### 2.1 원래 용어 유지

개발 용어를 완전히 없애지 않는다. 원래 용어를 유지하고 처음 등장할 때 짧고 쉬운 설명을 붙인다.

예시:

> API(프로그램끼리 정보를 주고받는 연결 통로)

### 2.2 처음 등장할 때만 설명

같은 보고서에서 같은 용어를 반복해서 설명하지 않는다. 이후에는 원래 용어만 사용할 수 있다.

### 2.3 필요한 용어만 설명

다음 중 하나에 해당할 때 설명을 고려한다.

* 작업 결과를 이해하는 데 필요함
* 위험도나 검증 결과를 이해하는 데 필요함
* 사용자가 직접 설정하거나 확인해야 함
* 비개발자가 오해할 가능성이 높음

문맥상 이해할 수 있는 일반 단어에는 설명을 붙이지 않는다.

### 2.4 기술적 의미 유지

쉽게 설명하더라도 용어의 범위를 다른 개념으로 바꾸지 않는다. 비유를 사용하는 경우에도 실제 정의를 먼저 제공한다.

## 3. 설명 깊이와 길이

### 3.1 기본 설명

일반 작업 보고서는 짧은 괄호 설명을 기본으로 한다.

예시:

> 입력 검증(입력한 값이 필요한 조건에 맞는지 먼저 확인하는 기능)

### 3.2 추가 설명

다음 경우에만 현재 작업에서의 역할을 한 문장 더 설명한다.

* 해당 용어가 변경의 핵심임
* 사용자가 직접 승인하거나 확인해야 함
* 일반 정의만으로 이번 변경을 이해하기 어려움

별도 용어 질문이나 승인에 중요한 개념인 경우에만 긴 개념 설명을 제공한다.

### 3.3 길이 제한

단순 작업 보고서에서는 설명할 용어를 최대 3개까지 우선한다. 같은 설명을 반복하지 않는다.

보안, 데이터 손실, 권한, 비밀정보와 직접 관련된 용어는 정확한 이해에 필요한 범위에서 이 제한을 넘을 수 있다.

## 4. 기술 전용 용어와 문맥 용어

### 4.1 특정 기술에만 해당하는 용어

다음 용어는 프로젝트가 해당 기술 구조를 사용하는 것이 확인된 경우에만 그 정의를 적용한다.

* `Props`: React Component에 전달되는 값인 경우
* `Hook`: React의 상태나 기능 재사용 방식인 경우
* `Component`: 프로젝트가 Component 구조를 사용하는 경우

React가 아닌 프로젝트에 React 전용 정의를 일반 규칙처럼 적용하지 않는다.

### 4.2 프로젝트에 따라 의미가 달라지는 용어

다음 용어는 일반적인 뜻과 현재 프로젝트에서의 역할을 구분한다.

* Session
* Token
* Middleware
* Event
* Route
* State

일반 정의를 먼저 쓰고, 프로젝트 역할을 확인한 경우에만 다음 문장으로 현재 역할을 설명한다.

역할을 확인하지 못했다면 확정 표현 대신 다음과 같이 작성한다.

> 코드 구조상 검색 기능에 사용되는 Route로 예상되지만, 전체 연결 관계는 확인하지 못했습니다.

### 4.3 IDE와 AI Agent 실행 환경

IDE는 코드를 작성하고 실행하는 개발 도구라는 일반 정의로 설명한다. AI Agent가 파일을 읽고 수정하는 실행 환경을 자동으로 IDE라고 부르지 않는다.

현재 환경이 실제 IDE인지 확인한 경우에만 IDE라는 표현을 사용한다.

## 5. 용어와 근거

용어의 일반적인 뜻은 reference 사전에서 가져올 수 있다. 파일이나 프로젝트에서 해당 용어가 맡는 역할을 설명할 때는 다음 기준을 따른다.

* 실제 파일 내용이나 연결 관계를 확인하면 확정 표현을 사용함
* 파일명이나 폴더명만 보고 판단하면 예상 표현을 사용함
* 중요한 역할 주장에는 가능한 경우 근거 출처를 표시함
* 모든 파일 설명에 같은 근거 문구를 반복하지 않음

용어 설명 자체에는 보고서 상태를 붙이지 않는다. 다만 용어의 프로젝트 역할을 사실처럼 설명할 때는 `docs/BEGINNER_REPORT_SPEC.md`의 근거 출처와 확인 상태 규칙을 따른다.

## 6. 기본 사전에 없는 용어

기본 사전에 없는 용어는 다음 순서로 확인한다.

1. 현재 코드와 프로젝트 문맥을 확인한다.
2. 프로젝트 내부 문서나 공식 용어를 확인한다.
3. 공통 glossary reference를 확인한다.
4. 정확한 의미를 확인할 수 없으면 쉬운 설명을 추측하지 않는다.
5. 필요한 경우 원래 용어를 유지하고 다음처럼 표시한다.

   > 현재 문맥에서 정확한 의미를 확인하지 못했습니다.

프로젝트 내부 문서의 설명을 참고할 수 있지만, 코드와 실제 동작에 어긋나는 설명을 무조건 사실로 받아들이지 않는다.

## 7. 코드 블록 설명

사용자가 특정 코드나 파일 설명을 요청한 경우에만 코드 블록 설명을 제공한다. 전체 작업 보고서에서 모든 코드 블록을 설명하지 않는다.

다음 항목 중 작업 이해에 필요한 1~3개를 우선한다.

* 역할
* 실행 시점
* 입력값
* 처리 결과
* 영향 범위

위험하거나 중요한 코드 블록인 경우 필요한 항목을 추가할 수 있다. 모든 항목을 모든 블록에 강제로 적용하지 않는다.

설명 단위는 한 줄이 아니라 다음과 같은 기능 블록으로 묶는다.

* 하나의 함수
* 하나의 조건문 묶음
* 하나의 API 호출
* 하나의 화면 Component
* 하나의 데이터 처리 단계

## 8. 파일 역할 설명

주요 파일은 경로만 나열하지 않고 역할을 한 문장으로 설명한다.

* 파일 내용이나 연결 관계를 확인한 경우 확정 표현을 사용함
* 파일명만 보고 판단한 경우 예상 표현을 사용함
* 중요한 파일 역할 주장에는 가능한 경우 근거를 연결함
* 자동 생성 파일과 잠금 파일은 역할을 확인한 경우에만 자세히 설명함

주요 파일의 수와 보고서 위치는 `docs/BEGINNER_REPORT_SPEC.md`와 `references/report-format.md`를 따른다.

## 9. 비밀정보 보호

용어 설명, 예시, 파일 역할 설명에 API 키, 비밀번호, 토큰, 쿠키, 연결 문자열, 개인정보의 실제 값을 포함하지 않는다. 변수 이름만 표시할 수 있다.

## 10. V0.1 시나리오 적용

### 시나리오 A

버튼 문구와 색상만 바꾸는 작업에는 불필요한 개발 용어를 추가하지 않는다. Component나 스타일 구조가 보고서 이해에 필요할 때만 짧게 설명한다.

### 시나리오 B

`입력 검증`은 다음 의미를 전달해야 한다.

> 검색어가 필요한 조건에 맞는지 검색 실행 전에 먼저 확인하는 기능

다음처럼 어려운 구현 용어만 나열하지 않는다.

> Submit handler에 validation guard를 추가했습니다.

## 11. 품질 점검

* [ ] 원래 용어를 유지했는가
* [ ] 필요한 용어만 처음 등장할 때 설명했는가
* [ ] 설명이 원래 용어보다 어렵지 않은가
* [ ] 기술적 의미를 왜곡하지 않았는가
* [ ] 특정 기술의 정의를 다른 프로젝트에 일반화하지 않았는가
* [ ] 프로젝트 역할을 확인하지 않고 확정하지 않았는가
* [ ] 기본 사전에 없는 용어를 추측하지 않았는가
* [ ] 코드 블록 설명 범위를 필요한 만큼으로 제한했는가
* [ ] 보고서 길이를 불필요하게 늘리지 않았는가
* [ ] 비밀정보를 포함하지 않았는가
