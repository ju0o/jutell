# JuTell — Beginner Report Specification

## 1. 문서 목적

이 문서는 AI Agent가 작업 결과를 비개발자에게 보고할 때 지켜야 할 핵심 실행 기준을 정의한다. 현재 실제 적용 Provider는 Codex(정식 지원), OpenCode·Claude Code(베타)이며, 규칙은 Provider에 종속되지 않도록 작성한다.

제품의 목적과 버전 범위는 `docs/PRODUCT_SCOPE.md`에서 정의한다.

이 문서는 다음 내용만 정의한다.

* 보고서 기본 구조
* 근거 출처
* 확인 상태
* 검증 결과
* 위험도
* 사용자 행동
* 최종 보고서 상태
* 보고서 길이
* 예외 처리

긴 예시, 용어 사전, 위험도 세부 사례, 테스트 시나리오의 정답표는 별도 문서에서 정의한다.

---

## 2. 적용 상황

이 명세는 다음 상황에 적용한다.

### 2.1 코드 또는 프로젝트 파일을 변경한 경우

AI Agent가 파일을 생성, 수정 또는 삭제한 뒤 최종 작업 결과를 보고할 때 적용한다.

### 2.2 변경 내용 설명을 요청받은 경우

사용자가 현재 프로젝트의 변경 내용을 쉬운 말로 설명해달라고 요청한 경우 적용한다.

이 경우 사용자가 별도로 요청하지 않았다면 코드를 수정하지 않는다.

### 2.3 특정 코드나 파일 설명을 요청받은 경우

전체 작업 보고서를 생성하지 않고 요청받은 코드나 파일만 설명한다.

### 2.4 구현 계획을 요청받은 경우

완료 보고서가 아니라 예상 변경 범위와 검증 계획을 설명한다.

실제로 변경하지 않은 내용을 완료한 것처럼 표현하지 않는다.

### 2.5 적용하지 않는 경우

다음 상황에는 전체 보고서 형식을 강제로 적용하지 않는다.

* 일반적인 개발 개념 질문
* 간단한 용어 뜻 질문
* 프로젝트와 관계없는 대화
* 사용자가 명시적으로 다른 형식을 요청한 경우

## 3. 사용자 요청 우선 원칙

사용자가 결과 보고 형식을 명시하면 가능한 범위에서 해당 형식을 따른다.

다만 다음 규칙은 생략하지 않는다.

* 확인하지 않은 내용을 사실처럼 표현하지 않음
* 테스트하지 않은 내용을 통과했다고 표현하지 않음
* 비밀정보를 출력하지 않음
* 실패 또는 미확인 상태를 숨기지 않음

사용자가 “코드만 수정하고 보고서는 작성하지 말라”고 요청한 경우에는 긴 보고서를 생성하지 않는다.

대신 작업이 끝난 뒤 최소한 다음만 짧게 알린다.

* 작업 완료 여부
* 수정한 주요 파일
* 실패하거나 확인하지 못한 중요한 항목

예시:

> 요청한 코드 수정은 완료했습니다.
> 주요 수정 파일은 `LoginForm.tsx`입니다.
> 브라우저 화면은 확인하지 못했습니다.

사용자가 답변 자체를 원하지 않는다고 명확히 요청했더라도 안전, 실패, 데이터 손실 가능성 또는 비밀정보 노출 문제가 발견되면 해당 내용은 알린다.

## 4. 기본 보고 구조

코드 변경 작업의 기본 보고서는 다음 6개 항목을 사용한다.

1. 변경 요약
2. 사용자에게 달라지는 점
3. 프로그램 내부에서 달라진 점
4. 주요 수정 파일
5. 검증 결과
6. 위험과 사용자 확인

필요한 경우 마지막에 다음 항목을 추가한다.

* 완료에 필수적인 미확인 (있을 때만 — `보고서 상태` 바로 앞에 적는다)
* 보고서 상태

단순한 작업에서는 보고서 상태를 6번 항목에 함께 작성할 수 있다.

내용이 없는 항목은 짧게 표시하거나 생략할 수 있다.

예시:

> 사용자에게 달라지는 점: 없음

## 5. 보고서 길이 기준

### 5.1 단순 작업

다음과 같은 작업은 단순 작업으로 본다.

* 문구 변경
* 색상 변경
* 간단한 여백 조정
* 문서 수정
* 주석 수정
* 한 파일 안의 작은 화면 변경

단순 작업 보고서는 다음 기준을 따른다.

* 각 기본 항목은 최대 1~2문장
* 주요 파일은 최대 3개
* 전체 보고서는 기본적으로 12문장 이내
* Markdown 기준 약 25줄 이내를 우선
* 같은 내용을 다른 항목에서 반복하지 않음
* 전체 파일 목록을 기본으로 출력하지 않음
* 위험, 실패 또는 중요한 미확인 사항이 없으면 상세 설명을 추가하지 않음

안전 문제, 테스트 실패, 비밀정보 노출 또는 데이터 손실 가능성이 있다면 길이 제한보다 정확한 경고를 우선한다.

### 5.2 일반 작업

특정 기능의 동작이 변경되거나 여러 파일이 수정된 경우다.

* 각 항목은 필요한 범위에서 작성
* 주요 파일은 최대 5개
* 검증 결과와 미확인 항목을 구분
* 영향 가능 기능이 있으면 설명

### 5.3 복잡하거나 위험한 작업

다음과 같은 작업은 세부 설명을 추가할 수 있다.

* 로그인
* 권한
* 결제
* 데이터베이스
* 외부 서비스
* 배포
* 공통 기능
* 비밀정보
* 여러 기능에 걸친 변경
* 테스트 실패가 있는 작업

길이를 늘리는 이유가 있어야 한다.

단순히 정해진 양식을 채우기 위해 보고서를 길게 만들지 않는다.

## 6. 정보 체계 분리

보고서에서는 다음 네 가지를 서로 다른 정보로 취급한다.

### 6.1 근거 출처

AI Agent가 무엇을 바탕으로 판단했는지를 나타낸다.

### 6.2 확인 상태

해당 내용이 어느 정도 확인됐는지를 나타낸다.

### 6.3 사용자 행동

사용자가 직접 확인하거나 결정해야 할 사항을 나타낸다.

### 6.4 보고서 상태

현재 작업 전체의 최종 상태를 나타낸다.

이 네 가지를 같은 표현으로 섞지 않는다.

---

## 7. 근거 출처

근거 출처는 다음 중 하나 이상을 사용한다.

### 7.1 파일

실제 파일 내용을 읽어서 확인했다.

표기 예시:

> 근거: 파일

### 7.2 Git

Git 상태, diff 또는 커밋 정보를 확인했다.

표기 예시:

> 근거: Git diff

### 7.3 명령

테스트, 빌드, 검사 또는 실행 명령의 결과를 확인했다.

표기 예시:

> 근거: `npm test` 실행 결과

### 7.4 브라우저 또는 실제 실행

브라우저나 실행 중인 프로그램에서 직접 확인했다.

표기 예시:

> 근거: `/login` 페이지 브라우저 확인

### 7.5 코드 예상

실제로 실행하지 않고 코드 내용만으로 예상했다.

표기 예시:

> 근거: 코드 예상

### 7.6 사용자 제공 정보

사용자가 제공한 설명, 이미지 또는 결과를 기준으로 판단했다.

표기 예시:

> 근거: 사용자 제공 화면

근거가 없는 내용을 확인된 사실처럼 작성하지 않는다.

### 7.7 근거 표기 범위

모든 문장에 근거와 확인 상태를 반복해서 붙이지 않는다.

다음과 같은 중요한 주장에는 근거와 확인 상태를 명시한다.

* 기능이 실제로 변경됐다는 주장
* 테스트가 통과하거나 실패했다는 주장
* 사용자 화면에서 결과를 확인했다는 주장
* 기존 기능에 영향이 없다는 주장
* 위험도 판단의 근거
* 데이터, 인증, 권한, 결제 또는 배포 관련 주장

같은 근거로 이어지는 여러 문장은 하나의 항목으로 묶을 수 있다.

예시:

> 확인 상태: 확인됨
> 근거: 파일과 Git diff
> 로그인 버튼 문구와 스타일 파일이 수정됐습니다.

단순한 안내 문장이나 이미 근거가 명확한 파일 설명에는 상태를 반복하지 않아도 된다.

## 8. 확인 상태

확인 상태는 다음 세 가지로 단순화한다.

### 8.1 확인됨

근거를 직접 확인했다.

예시:

> 확인 상태: 확인됨
> 근거: 파일
> 버튼 문구가 “로그인하기”로 변경됐습니다.

확인됨은 확인한 범위에만 적용한다.

파일을 읽었다고 해서 실제 화면이나 전체 기능까지 확인된 것은 아니다.

### 8.2 일부 확인

일부 근거는 확인했지만 전체 동작이나 필요한 모든 환경을 확인하지 못했다.

예시:

> 확인 상태: 일부 확인
> 빌드는 통과했지만 실제 로그인 동작은 확인하지 못했습니다.

### 8.3 확인하지 못함

필요한 근거를 확보하지 못했다.

예시:

> 확인 상태: 확인하지 못함
> 브라우저를 실행할 수 없어 실제 화면을 확인하지 못했습니다.

### 8.4 예상 표현

코드 예상은 확인 상태와 별도로 표시한다.

예시:

> 확인 상태: 확인하지 못함
> 근거: 코드 예상
> 버튼이 파란색으로 표시될 것으로 예상됩니다.

코드 예상만으로 `확인됨`을 사용하지 않는다.

## 9. 사용자 행동

사용자 행동은 다음 중 필요한 항목만 작성한다.

### 9.1 사용자 확인 필요

사용자가 화면이나 실제 동작을 직접 확인해야 한다.

예시:

> 사용자 확인 필요: 모바일 화면에서 버튼이 잘리지 않는지 확인해주세요.

### 9.2 추가 테스트 요청 권장

현재 검증만으로는 충분하지 않다.

예시:

> 추가 테스트 권장: 로그인 성공, 실패, 로그아웃 흐름을 함께 확인해주세요.

### 9.3 설정 필요

사용자가 환경변수나 외부 설정을 입력해야 한다.

예시:

> 설정 필요: `WEATHER_API_KEY` 환경변수를 등록해야 합니다. 실제 값은 보고서에 표시하지 않았습니다.

### 9.4 사용자 결정 필요

여러 방식 중 사용자의 제품 결정이 필요하다.

예시:

> 사용자 결정 필요: 로그인 유지 기간을 7일과 30일 중 선택해야 합니다.

### 9.5 다음 행동 제안

`nextActionSuggestions`가 활성일 때 보고서 마지막에 다음 행동 제안을 **최대 3개**만 추가한다. 다음 경우에만 제안한다.

* 사용자가 직접 확인해야 할 항목이 남은 경우
* 검증되지 않아 보류된 항목이 있는 경우
* 설정이 필요한 경우
* 데이터 손실·보안 위험이 확인된 경우

예시:

> 다음 행동 제안:
> - 실제 화면에서 검색 버튼을 눌러 확인해주세요.
> - `WEATHER_API_KEY` 설정을 마치면 결과를 다시 확인해주세요.

제안은 보고서에서 이미 확인된 항목 중에서만 고르고, 추측이나 새 작업을 제안하지 않는다. 해당하지 않으면 생략한다. 사용자 행동이 없으면 억지로 항목을 만들지 않는다.

## 10. 검증 결과

검증 결과는 다음 상태 중 하나를 사용한다.

### 10.1 통과

실행한 검증이 성공했다.

### 10.2 일부 통과

실행한 검증 중 일부만 성공했다.

### 10.3 실패

검증이 실패했다.

### 10.4 실행하지 못함

도구, 권한, 설정 또는 환경 문제로 실행하지 못했다.

### 10.5 실행하지 않음

검증이 가능할 수 있지만 이번 작업에서 실행하지 않았다.

### 10.6 검증 수단 없음

프로젝트에서 사용할 수 있는 테스트나 확인 방법을 찾지 못했다.

검증 결과에는 가능한 경우 다음을 함께 기록한다.

* 실행한 명령
* 확인 범위
* 실패 개수
* 실행하지 못한 이유

전체 로그를 그대로 출력하지 않는다.

---

## 11. 검증 결과와 보고서 상태 연결

검증 결과와 최종 보고서 상태는 다음 기준으로 연결한다.

### 11.1 연결표

| 검증 상황                               | 기본 보고서 상태      |
| ----------------------------------- | -------------- |
| 필요한 핵심 검증이 모두 통과했고 중요한 미확인 사항이 없음   | 확인 완료          |
| 핵심 검증은 통과했지만 실제 화면이나 사용자 환경 확인이 필요함 | 추가 확인 필요       |
| 필요한 테스트를 실행하지 않음                    | 추가 확인 필요       |
| 프로젝트에 테스트 방법 자체가 없음                 | 추가 확인 필요       |
| 브라우저 확인만 실패하거나 실행하지 못함              | 추가 확인 필요       |
| 일부 테스트만 실행함                         | 일부 확인          |
| 보조 테스트만 실패하고 핵심 기능은 통과함             | 일부 확인          |
| 핵심 테스트가 실패함                         | 작업 보류          |
| 빌드가 실패함                             | 작업 보류          |
| 실행 권한이 없어 핵심 검증을 수행하지 못함            | 일부 확인 또는 작업 보류 |
| 필수 도구가 없어 핵심 검증을 수행하지 못함            | 일부 확인 또는 작업 보류 |
| 사용자의 필수 설정이나 결정이 남아 있음              | 추가 확인 필요       |
| 안전 또는 보안 문제가 발견됨                    | 작업 보류          |
| 요청한 핵심 기능을 구현하지 못함                  | 작업 보류          |
| 요청이 현재 작업이나 Skill의 범위를 벗어남          | 범위 밖           |

### 11.2 실행 권한 또는 도구가 없는 경우

실행 권한이나 도구가 없을 때는 해당 검증의 중요도에 따라 결정한다.

* 보조 검증을 실행하지 못함: `추가 확인 필요`
* 핵심 검증을 일부만 수행함: `일부 확인`
* 핵심 기능을 전혀 검증할 수 없음: `작업 보류`

### 11.3 중요한 미확인 사항

다음 항목은 기본적으로 중요한 미확인 사항으로 본다.

* 로그인
* 인증
* 사용자 권한
* 결제
* 데이터 저장과 삭제
* 데이터베이스 구조
* 비밀정보 처리
* 외부 서비스 연결
* 배포 설정
* 여러 기능이 사용하는 공통 코드
* 사용자의 파일이나 데이터를 변경하는 기능
* 되돌리기 어려운 작업

이번 요청에서는 다음도 중요한 미확인 사항으로 본다.

* 이번 요청이 실제로 원하는 결과(직접 범위)를 만들어냈는지
* 사용자가 명시했거나 요청 자체로 명백한 건드리지 말 것
* 사용자가 명시했거나 요청 자체로 명백한 유지할 것
* 사용자가 이번 요청에서 완료 조건으로 직접 말한 것(예: 테스트 통과, 모바일 화면 확인)

위 항목과 직접 관련된 핵심 동작을 확인하지 못했다면 `확인 완료`를 사용하지 않는다. 이번 요청과 직접 관련 없는 다른 검증이 빠졌다는 이유만으로 `확인 완료`를 막지는 않는다.

관련 검증이 통과했다는 사실만으로 이 판단을 덮어쓰지 않는다. 위 항목 중 하나가 이번 요청 결과의 실제 성공에 필수인데도 확인되지 않았거나 실패한 상태라는 것을 Agent가 이미 알고 있다면, 관련 테스트가 통과했더라도 `확인 완료`를 사용하지 않는다 — 검증은 실제로 다룬 범위만 증명한다. 이때는 §4의 `완료에 필수적인 미확인` 항목에 무엇이 미확인·실패 상태인지 짧게 적는다.

예:

> 완료에 필수적인 미확인: 외부 신원 인증 서비스 실제 연결
> 보고서 상태: 일부 확인

문구, 색상, 일반 여백처럼 핵심 동작에 영향을 주지 않는 시각적 확인만 남은 경우에는 이 항목을 만들지 않고 `추가 확인 필요`를 사용할 수 있다.

### 11.4 우선순위

여러 상태에 동시에 해당하면 다음 순서로 더 보수적인 상태를 적용한다.

1. 작업 보류
2. 일부 확인
3. 추가 확인 필요
4. 확인 완료

`범위 밖`은 작업 자체가 대상이 아닐 때 별도로 사용한다.

### 11.5 상태의 의미

`확인 완료`는 프로젝트 전체가 완벽하게 정상 작동한다는 의미가 아니다.

AI Agent가 확인한 작업 범위 안에서 필요한 검증이 완료됐다는 의미다.

다만 이 "확인한 작업 범위"를 이용해 완료에 필수적인 미확인·실패를 조용히 빼놓을 수는 없다. Agent가 이미 알고 있는 완료에 필수적인 미확인·실패가 남아 있으면, 그 항목을 단순히 확인 범위 밖으로 제외해서 `확인 완료`를 사용할 수 없다 — 그런 항목은 §4의 `완료에 필수적인 미확인` 항목에 적고, 이 항목이 있으면 `확인 완료`를 쓰지 않는다.

사용자의 승인과 배포 여부는 별도의 결정이다.

## 12. 위험도

위험도는 검증 상태와 별도로 판단한다.

실행 환경이 없다는 이유만으로 위험도를 `판정 불가`로 만들지 않는다.

### 12.1 낮음

프로그램 핵심 동작에 영향을 줄 가능성이 작은 변경이다.

예시:

* 일반 문구
* 색상
* 여백
* 단순 화면 배치
* 문서
* 주석

### 12.2 중간

특정 기능의 동작이나 한정된 사용자 흐름에 영향을 줄 수 있다.

예시:

* 버튼 동작
* 입력 검증
* 특정 페이지 이동
* 특정 기능의 상태 처리
* 특정 페이지 데이터 표시
* 로컬 저장 방식

### 12.3 높음

여러 기능, 중요한 데이터, 보안 또는 운영 환경에 영향을 줄 수 있다.

예시:

* 로그인
* 인증
* 권한
* 결제
* 데이터베이스 구조
* 공통 상태 관리
* 공통 API 처리
* 외부 서비스
* 비밀정보
* 배포 설정
* 여러 기능이 사용하는 공통 로직

### 12.4 판정 불가

코드나 변경 범위를 충분히 읽지 못해 위험 자체를 판단할 근거가 없는 경우다.

실행하지 못한 것과 위험도를 판단하지 못하는 것은 다르다.

예시:

* 코드를 읽었지만 실행하지 못함: 위험도 판단 가능
* 변경 파일을 열지 못함: 위험도 판정 불가 가능

### 12.5 위험도 우선순위

여러 조건에 해당하면 가장 높은 위험도를 적용한다.

다만 파일 이름만으로 판단하지 않고 실제 변경 내용을 기준으로 한다.

예시:

* 로그인 화면의 일반 문구만 변경: 낮음
* 로그인 처리 방식 변경: 높음
* 결제 버튼 색상만 변경: 낮음
* 결제 실행 조건 변경: 높음

위험도에는 짧은 근거를 함께 작성한다.

## 13. 브라우저 사용 범위

V0.1은 별도의 브라우저 자동화 기능을 제공하지 않는다.

다만 현재 AI Agent 실행 환경에 이미 브라우저 또는 화면 확인 도구가 제공되고, 사용자가 허용한 경우에는 선택적으로 사용할 수 있다.

브라우저 도구가 없으면 새 도구를 설치하거나 별도 서비스를 연결하지 않는다.

브라우저 확인 여부는 다음처럼 구분한다.

* 브라우저로 확인함
* 일부 화면만 확인함
* 브라우저 도구가 없음
* 브라우저 확인을 실행하지 않음
* 브라우저 실행 실패

브라우저를 확인하지 않았다면 시각적 결과를 확정적으로 표현하지 않는다.

## 14. 작업 시작 기준 상태

코드 변경 작업을 시작하기 전에 가능한 경우 다음 상태를 확인한다.

* Git 저장소 여부
* 현재 변경 파일
* 추적되지 않은 파일
* 현재 브랜치
* 기존 테스트 실패 여부

기준 상태를 확인하지 못한 경우 다음 원칙을 적용한다.

* 변경 출처를 자동으로 단정하지 않음
* AI Agent가 직접 수정한 사실이 명확한 파일만 이번 작업 변경으로 보고
* 나머지는 `출처 구분 불가`로 표시
* 기존 변경을 되돌리거나 덮어쓰지 않음

표현 예시:

> 출처 구분 불가: 작업 시작 전 Git 상태를 기록하지 않아 일부 변경이 이번 작업에서 발생했는지 판단하지 못했습니다.

## 15. 주요 파일 선정

기본적으로 최대 5개의 주요 파일만 설명한다.

단순 작업은 최대 3개를 우선한다.

선정 우선순위는 다음과 같다.

1. 사용자가 요청한 기능을 직접 구현한 파일
2. 사용자 화면이나 동작에 직접 영향을 주는 파일
3. 핵심 데이터 처리 파일
4. 공통 기능에 영향을 주는 파일
5. 인증, 권한, 데이터베이스, 설정 또는 배포 파일
6. 문제의 직접 원인이 있던 파일

### 15.1 같은 우선순위 파일이 많은 경우

같은 우선순위에 해당하는 파일은 다음 순서로 선정한다.

1. 사용자 화면이나 사용자 행동에 가장 가까운 파일
2. 요청한 기능의 실제 동작을 변경한 파일
3. 다른 변경 파일이 의존하는 상위 파일
4. 설정 파일보다 직접 작성된 기능 소스 파일
5. 테스트 파일보다 실제 기능 파일
6. 위 기준도 같다면 변경된 코드 줄 수가 더 많은 파일
7. 변경량까지 같다면 파일 경로의 알파벳 순서

다만 테스트 실패의 직접 원인이 테스트 파일에 있거나, 설정 파일이 보안·배포·의존성에 영향을 주는 경우에는 해당 파일을 주요 파일로 포함할 수 있다.


### 15.2 제외 우선 파일

다음 파일은 일반적으로 주요 파일에서 제외한다.

* 자동 생성 파일
* 단순 잠금 파일
* 기능 변화가 없는 포맷 수정
* 단순 스냅샷
* 기능에 직접 영향을 주지 않는 보조 파일

단, 의존성, 보안 또는 배포에 영향을 주면 주요 파일로 포함할 수 있다.

## 16. 비밀정보 보호 시점

비밀정보 보호는 최종 보고 단계에서만 수행하지 않는다.

다음 세 시점에서 확인한다.

### 16.1 명령 실행 전

AI Agent는 실행하려는 명령이 비밀정보를 화면에 출력할 가능성이 있는지 먼저 확인한다.

다음과 같은 명령은 그대로 실행하지 않는다.

* 전체 환경변수를 출력하는 명령
* 인증 헤더를 그대로 표시하는 명령
* 설정 파일 전체를 터미널에 출력하는 명령
* 쿠키, 세션 또는 토큰 값을 출력하는 디버그 명령
* 데이터베이스 연결 문자열을 표시하는 명령
* 비밀 값이 명령 인자에 직접 포함된 명령

피해야 할 예:

```text
env
printenv
set
curl -v -H "Authorization: Bearer 실제토큰"
cat .env
```

대신 다음과 같은 안전한 방법을 사용한다.

* 필요한 환경변수의 존재 여부만 확인
* 값 전체가 아니라 변수 이름만 확인
* 문자열 길이나 설정 여부만 확인
* 민감한 헤더를 제외한 옵션 사용
* 로그의 필요한 부분만 필터링
* 비밀 값 대신 환경변수 참조 사용

예시:

```text
WEATHER_API_KEY가 설정되어 있는지만 확인
```

비밀정보 출력 가능성을 안전하게 통제할 수 없다면 해당 명령을 실행하지 않고 다음처럼 보고한다.

> 실행하지 않음: 비밀정보가 출력될 가능성이 있어 해당 명령을 실행하지 않았습니다.


### 16.2 도구 출력 처리 중

명령 결과나 오류 로그에 다음 값이 포함됐는지 확인한다.

* API 키
* 비밀번호
* 접근 토큰
* 인증 헤더
* 쿠키
* 세션 값
* 연결 문자열
* 개인 식별 정보
* 환경변수 실제 값

도구 출력이 사용자에게 공개되기 전에 가능한 범위에서 값을 가린다.

### 16.3 최종 보고 전

보고서 전체를 다시 확인한다.

민감한 값은 다음처럼 처리한다.

* `[REDACTED]`
* `****`
* 변수 이름만 표시

### 16.4 이미 출력된 경우

도구가 비밀정보를 이미 대화 화면에 노출했다면 완전히 되돌릴 수 있다고 표현하지 않는다.

다음 행동을 안내한다.

* 해당 키 또는 토큰 폐기
* 새 값 발급
* 로그와 코드에서 값 제거
* 환경변수로 이동
* 필요하면 보안 담당자에게 알림

실제 비밀 값은 다시 반복 출력하지 않는다.

```text id="ga6ji0"
- 사용자 확인 필요: 실제 화면에서 문구가 잘리지 않는지 확인해주세요.
- 보고서 상태: 추가 확인 필요
```

## 19. 비개발자 평가 원칙

비개발자 평가의 구체적인 시나리오, 기대 답변, 채점 예시는 `docs/TEST_SCENARIOS.md`에서 정의한다.

이 문서에서는 다음 원칙만 고정한다.

* 같은 시나리오에는 같은 질문 사용
* 평가자는 전체 코드를 보지 않음
* 보고서만 읽고 답변
* 정확한 개발 용어보다 의미 이해를 평가
* 실제 확인과 예상을 혼동하면 실패
* 사용자 확인 항목을 찾지 못하면 실패
* 7개 질문 중 6개 이상 통과해야 이해 가능

평가 질문은 다음과 같다.

1. 무엇이 바뀌었는가
2. 사용자에게 무엇이 달라지는가
3. 프로그램 내부에서는 무엇이 달라졌는가
4. 무엇을 실제로 확인했는가
5. 무엇을 확인하지 못했는가
6. 사용자가 무엇을 확인해야 하는가
7. 현재 추가 확인이 필요한가

`docs/TEST_SCENARIOS.md`에 검증 시나리오, 기대 답변, 채점 기준이 작성되기 전에는 비개발자 이해 평가가 완료됐다고 판정하지 않는다.

평가 문서가 준비되지 않은 상태에서는 다음처럼 표시한다.

> 평가 상태: 준비 중
> 비개발자 평가 시나리오와 채점표가 아직 확정되지 않았습니다.

## 20. 금지 표현

근거가 없으면 다음 표현을 사용하지 않는다.

* 완벽하게 작동합니다
* 모든 문제가 해결됐습니다
* 오류가 전혀 없습니다
* 기존 기능에 영향이 없습니다
* 배포해도 됩니다
* 안전합니다
* 모든 테스트가 통과했습니다
* 화면이 정상적으로 표시됩니다

대신 확인한 범위를 정확하게 작성한다.

예시:

> 로그인 관련 테스트 4개는 통과했습니다. 전체 테스트와 실제 브라우저 로그인은 확인하지 못했습니다.
