# JuTell 개인 베타 실행 안내

이 문서는 현재 구현된 로컬 관리자와 JuTell Skill을 실제 프로젝트에서 안전하게 사용하기 위한 실행 순서입니다. 이번 단계는 기능 추가나 공개 베타 판정이 아니라, 작은 작업을 반복해서 사용하고 이해하기 어려운 점을 기록하는 단계입니다.

## 1. 첫 실행 체크리스트

### 관리자 실행

- [ ] 프로젝트 루트에서 `apps/local-admin/`으로 이동합니다.
- [ ] 필요하면 `npm install`을 실행하고 `npm run dev`로 로컬 관리자를 엽니다.
- [ ] `http://127.0.0.1:5174`에서 Overview를 확인합니다.
- [ ] 설정 파일이 정상인지 확인합니다.
- [ ] Skill과 `AGENTS.md`가 준비됨으로 표시되는지 확인합니다.
- [ ] 외부 전송 없음, 중앙 서버 없음이 표시되는지 확인합니다.

### 설정 선택

- [ ] 사용할 Profile을 고릅니다.
- [ ] 활성 Feature와 비활성 Feature를 확인합니다.
- [ ] Limits를 쉬운 단계로 고릅니다.
- [ ] 저장 전 미리보기에서 바뀌는 내용을 읽습니다.
- [ ] 문제가 없을 때만 설정을 저장합니다.

### AI Agent Provider에 적용

관리자 화면을 열었다고 현재 AI Agent 세션에 설정이 자동 적용되는 것은 아닙니다. 현재 실제 연결 Provider는 Codex(정식 지원), OpenCode·Claude Code(베타)이며, 새 작업을 시작할 때 아래 문구를 그대로 전달합니다.

```text
이 프로젝트의 AGENTS.md,
.agents/skills/beginner-bridge/SKILL.md,
.jutell.json을 먼저 읽고 작업해주세요.

작업 완료 후 현재 활성화된 JuTell 기능만 사용해 보고해주세요.
설정으로 꺼진 항목은 생략하되,
실패, 중요한 미확인 사항, 범위 밖 변경과 안전 문제는 숨기지 마세요.
```

### 작업 후 평가

작업마다 다음을 짧게 확인합니다.

- [ ] 보고서가 작업에 비해 너무 길거나 짧지 않은가
- [ ] 어려운 말 없이 이해되는가
- [ ] 불필요한 항목이 있는가
- [ ] 빠진 정보가 있는가
- [ ] 실제 확인과 예상이 섞이지 않았는가
- [ ] 같은 설정을 다시 사용할 수 있는가
- [ ] 반복되거나 중요한 문제만 Beta Journal에 기록했는가

## 2. 첫 실사용 테스트

실제 프로젝트 전체를 한 번에 맡기지 말고, 되돌리기 쉬운 작은 작업 하나로 시작합니다. 다음 중 하나를 선택합니다.

- 문구 변경
- 버튼 색상 변경
- 간단한 안내 문구 추가
- 작은 입력 검증
- 문서 수정

첫 작업은 변경 전 Git 상태를 기록하고, 변경 범위를 한두 파일로 제한합니다. 작업이 끝나면 Skill 보고서와 실행한 검증만 확인합니다. 브라우저를 직접 보지 않았다면 화면 결과를 사실로 승인하지 않습니다.

첫 테스트에서는 다음 작업을 제외합니다.

- 로그인·인증
- 결제
- 데이터베이스
- 배포
- 환경변수와 API 키
- 외부 서비스 연결
- 대규모 리팩터링

## 3. Profile 비교 절차

Profile을 비교할 때는 비슷한 크기와 위험도의 작은 작업을 선택하되, 매번 서로 다른 작업을 사용합니다. 각 Profile을 최소 2회 사용한 뒤 판단합니다. 한 번의 보고서만 보고 Profile의 우열을 결정하지 않습니다.

| Profile | 확인할 내용 |
|---|---|
| `minimal` | 보고서가 충분히 짧은가, 필요한 검증 정보가 남는가, 너무 많은 정보가 사라지지 않는가 |
| `balanced` | 기본 사용에 자연스러운가, 파일·검증·위험 설명이 과하지 않은가 |
| `learning` | 용어 설명이 실제 학습에 도움이 되는가, 설명 때문에 보고서가 지나치게 길어지지 않는가 |
| `detailed` | 복잡하거나 위험한 작업에서 유용한가, 단순 작업에서는 과도하지 않은가 |

각 사용 후 Profile, 작업 종류, 보고서 길이 체감, 이해하기 어려웠던 부분, 다시 사용할 의향을 짧게 기록합니다. Profile 차이만으로 기능 오류라고 단정하지 말고, 실제 설정과 보고서를 함께 확인합니다.

## 4. Feature 비교 절차

기준 설정을 먼저 확인한 뒤 한 번에 하나의 Feature만 바꿉니다. 모든 Feature를 동시에 끄거나 켜면 어떤 기능의 영향인지 알 수 없습니다.

권장 순서는 다음과 같습니다.

1. `internalChanges`
2. `mainFiles`
3. `glossary`
4. `riskAssessment`
5. `userVisibleChanges`
6. `validationResults`
7. `userActions`
8. `changeSummary`

각 Feature마다 다음을 기록합니다.

- 켰을 때 실제로 도움이 됐는가
- 껐을 때 보고서가 더 좋아졌는가
- 꺼도 중요한 정보가 남았는가
- 기본 ON과 기본 OFF 중 어느 쪽이 적절한가
- 특정 Profile에서만 필요한가

순서의 마지막 세 항목인 `validationResults`, `userActions`, `changeSummary`는 검증·다음 행동·변경 이해에 직접 연결되므로 더 보수적으로 확인합니다. `userVisibleChanges`도 화면 확인과 관련되므로 화면을 직접 보지 못한 경우 예상 표현인지 확인합니다. 실패, 중요한 미확인 사항, 보안·데이터 손실 위험은 Feature를 꺼도 숨겨지지 않아야 합니다.

## 5. Beta Journal 기록 기준

모든 작업을 기록하지 않습니다. 다음 경우에만 짧은 기록을 남깁니다.

- 같은 불편이 두 번 이상 반복됨
- 사실과 다른 설명을 발견함
- 중요한 정보가 빠짐
- Feature 설정과 실제 보고가 다름
- 보고서가 지나치게 길거나 짧음
- 용어 설명이 틀리거나 오히려 어려움
- Profile 차이를 이해하기 어려움
- 설정 저장이나 복원이 불안하거나 실패함
- 기록 삭제 결과가 기대와 다름
- 안전 정보가 숨겨짐

단순한 취향 차이는 사용을 막지 않는다면 낮은 심각도로 기록합니다. 기록에는 Prompt, 코드, 파일 경로, 오류 원문, 프로젝트 식별 정보, 비밀정보를 넣지 않습니다. 문제를 한 문장으로 요약하고, 사용한 Profile·Feature·심각도·현재 상태만 남깁니다.

## 6. 문제 분류와 심각도

### 문제 범주

- **UI 설명 문제**: 화면의 문구나 안내가 이해하기 어려움
- **Profile 설계 문제**: Profile 이름·차이·추천 대상이 실제 기대와 다름
- **Feature 동작 문제**: 켜고 끈 결과가 설정과 다름
- **보고서 길이 문제**: 작업에 비해 너무 길거나 짧음
- **용어 설명 문제**: 기술 용어 설명이 틀리거나 문맥과 다름
- **사실 정확성 문제**: 확인하지 않은 내용이 사실처럼 보고됨
- **검증 상태 문제**: 실행한 검증, 실행하지 못한 검증, 보고서 상태가 맞지 않음
- **설정 저장 문제**: 저장·복원·삭제가 실패하거나 기존 설정을 잘못 바꿈
- **개인정보·안전 문제**: 비밀정보 노출, 안전 정보 은폐, 원치 않는 전송 가능성
- **설치·실행 문제**: 관리자나 Skill을 시작할 수 없음
- **새로운 기능 요청**: 현재 범위에 없는 아이디어나 확장 요구

### 심각도

- **낮음**: 불편하지만 작업과 사용은 가능함
- **중간**: 이해나 사용을 반복적으로 방해함
- **높음**: 잘못된 판단이나 기능 오작동이 생길 수 있음
- **치명적**: 데이터 손실, 비밀정보 노출, 안전 정보 은폐가 발생함

여러 범주에 해당하면 더 위험한 쪽을 우선합니다. 사실 오류와 안전 문제는 한 번만 발생해도 기록하고 즉시 사용을 멈출지 판단합니다.

## 7. 구현 작업으로 넘기는 조건

다음 중 하나라도 해당할 때만 다음 수정 작업을 검토합니다.

- 같은 문제가 두 번 이상 반복됨
- 사실 오류가 한 번이라도 발생함
- 안전 관련 문제가 발견됨
- Feature 설정과 실제 보고가 다름
- 설정 저장 또는 삭제가 실패함
- Profile이 사용자에게 잘못된 기대를 줌
- 개인 베타를 진행할 수 없는 UI 문제가 있음

새로운 아이디어가 떠올랐다는 이유만으로 바로 구현하지 않습니다. 먼저 Beta Journal에 기록하고, 반복성·영향·안전성을 확인한 뒤 수정 목록에 넣습니다.

## 8. 개인 베타 종료 조건

개인 베타는 날짜가 아니라 다음 조건을 모두 확인한 뒤 종료합니다.

- 실제 프로젝트 3개 이상에 적용함
- 보고서 20개 이상을 검토함
- 네 Profile을 각각 최소 2회 사용함
- 주요 Feature를 각각 ON/OFF 비교함
- 반복 문제 목록을 작성함
- 기본 추천 Profile 후보를 정함
- 기본 OFF 후보 Feature를 정함
- 반드시 유지할 안전 정보를 확인함
- 치명적 문제가 없음
- 공개 베타 전에 수정할 목록을 확정함

이 조건을 충족하기 전에는 공개 베타나 V1 완료로 표현하지 않습니다.
