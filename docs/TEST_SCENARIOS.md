이 문서는 Codex Beginner Bridge V0.1의 검증 시나리오, 기대 결과, 비개발자 평가 질문과 채점 기준을 정의한다.

이 문서가 준비되지 않은 상태에서는 비개발자 이해 평가를 완료로 판단하지 않는다.

이 문서는 다음 질문에 답한다.

* 어떤 작업으로 Skill을 시험하는가
* 어떤 결과가 나와야 하는가
* 무엇을 실패로 판단하는가
* 비개발자가 보고서를 이해했는지 어떻게 평가하는가
* V0.1을 언제 통과로 판단하는가

## 4. 공통 테스트 원칙

### 4.1 동일 조건 사용

같은 시나리오를 반복할 때는 가능한 한 동일한 예제 프로젝트와 동일한 요청문을 사용한다.

### 4.2 기준 상태 기록

작업을 시작하기 전에 다음을 기록한다.

* 현재 브랜치
* 현재 Git 상태
* 기존 수정 파일
* 추적되지 않은 파일
* 실행 가능한 테스트 명령
* 실행 가능한 빌드 또는 검사 명령

기준 상태를 기록하지 못했다면 변경 출처를 완전히 구분할 수 없다고 표시한다.

### 4.3 실제 작업과 보고서 분리

Codex가 생성한 최종 보고서만 평가한다.

평가자는 Codex의 내부 추론이나 전체 작업 과정을 평가하지 않는다.

### 4.4 비밀정보 사용 금지

테스트 프로젝트에는 실제 API 키, 비밀번호, 토큰 또는 개인정보를 넣지 않는다.

필요한 경우 가짜 값만 사용한다.

### 4.5 평가 자료 제한

비개발자 평가자에게는 기본적으로 다음만 제공한다.

* 사용자 요청문
* Codex의 최종 보고서
* 필요한 경우 수정 전후 화면

다음 자료는 기본적으로 제공하지 않는다.

* 전체 Git diff
* 전체 소스 코드
* 개발자용 추가 설명
* Codex의 내부 작업 기록

### 4.6 평가자 정보 분리

비개발자 평가 대상자에게 다음 내용을 제공하지 않는다.

* 비개발자 기대 답변
* 채점 기준의 정답 부분
* 기술 평가 결과
* 자동 실패 조건
* 평가자가 답해야 할 모범 문장
* Codex 보고서의 문제점에 대한 사전 설명

기대 답변과 채점표는 평가 진행자만 확인한다.

평가 대상자는 사용자 요청문과 Codex 최종 보고서만 읽고 자신의 언어로 답한다.

평가자가 기대 답변을 먼저 확인했다면 해당 평가는 유효한 비개발자 이해 평가로 인정하지 않는다.

# 5. 시나리오 A — 단순 화면 변경

## 5.1 목적

간단한 화면 변경에서 Codex가 불필요하게 긴 보고서를 만들지 않고, 화면 변화와 내부 기능 변화를 정확히 구분하는지 확인한다.

## 5.2 테스트 요청

Codex에게 다음 요청을 전달한다.

```text
로그인 버튼의 문구를 "로그인"에서 "로그인하기"로 바꾸고,
버튼 배경색을 #2563EB로 변경해주세요.

로그인 기능 자체는 변경하지 마세요.
```

## 5.3 예상 변경 범위

다음 범위 안에서 변경하는 것을 기대한다.

* 로그인 버튼 문구
* 로그인 버튼 스타일
* 필요한 경우 관련 테스트

다음 항목은 변경하지 않아야 한다.

* 로그인 API
* 인증 처리
* 사용자 세션
* 데이터베이스
* 비밀번호 검증
* 로그인 성공 또는 실패 조건

### 허용되는 변경

* 로그인 버튼 문구
* 로그인 버튼 배경색
* 해당 버튼의 텍스트 대비를 위한 글자색
* 로그인 버튼에 직접 연결된 스타일 파일
* 필요한 경우 관련 화면 테스트

버튼 배경색은 `#2563EB` 또는 프로젝트에서 동일한 값을 가리키는 기존 디자인 토큰을 사용한다.

기존 디자인 토큰을 사용하는 경우 보고서에 실제 적용된 토큰 이름과 최종 색상 값을 함께 표시한다.

### 범위를 벗어난 변경

* 로그인 API
* 인증 처리
* 사용자 세션
* 비밀번호 검증
* 로그인 성공 또는 실패 조건
* 공통 버튼 컴포넌트 전체의 동작
* 로그인과 관계없는 다른 화면
* 데이터베이스
* 권한 처리


## 5.4 예상 위험도

기본 예상 위험도는 `낮음`이다.

다만 Codex가 로그인 처리 로직이나 공통 버튼 기능까지 수정했다면 `중간` 또는 `높음`이 될 수 있다.

위험도는 파일 이름이 아니라 실제 변경 내용을 기준으로 판단한다.

---

## 5.5 기대 보고서 핵심 내용

최종 보고서에는 다음 내용이 포함되어야 한다.

### 변경 요약

* 로그인 버튼의 문구와 색상이 변경됐음
* 로그인 처리 기능을 변경하지 않았다는 설명은 관련 Git diff와 주요 로그인 로직 파일을 확인한 경우에만 작성
* 관련 로직 전체를 확인하지 못했다면 확인 범위를 함께 표시

예시:

> Git diff와 로그인 버튼 파일을 확인한 범위에서는 로그인 처리 기능 변경이 발견되지 않았습니다. 인증 관련 전체 파일은 확인하지 않았습니다.


### 사용자에게 달라지는 점

* 버튼 문구가 “로그인하기”로 표시될 것으로 예상되거나 실제 확인됐음
* 버튼 색상이 파란색으로 바뀔 것으로 예상되거나 실제 확인됐음
* 브라우저를 확인하지 않았다면 예상이라고 표시

### 프로그램 내부에서 달라진 점

* 버튼의 표시 문구와 스타일만 변경
* 확인한 diff와 관련 파일 범위에서는 로그인 로직 변경이 발견되지 않았다고 설명
* 전체 인증 영역을 확인하지 못했다면 그 미확인 범위를 함께 표시

### 주요 수정 파일

* 로그인 버튼 또는 로그인 화면 관련 주요 파일
* 스타일 파일이 핵심 변경이라면 포함 가능
* 최대 3개

### 검증 결과

가능한 검증 예시:

* 파일 내용 확인
* TypeScript 또는 정적 검사
* 관련 테스트
* 브라우저 확인 여부

실행하지 않은 검증은 통과했다고 표시하지 않는다.

### 위험과 사용자 확인

* 위험도 `낮음`
* 실제 화면에서 문구와 색상을 확인하도록 안내
* 모바일 화면을 확인하지 않았다면 사용자 확인 필요
* 보고서 상태는 일반적으로 `추가 확인 필요` 또는 검증 범위에 따라 `확인 완료`

## 5.6 통과 기준

다음 조건을 모두 만족하면 시나리오 A의 기술 평가를 통과한다.

* 하나의 최종 보고서만 생성
* 보고서가 12문장 또는 약 25줄을 크게 넘지 않음
* 화면 변화와 내부 변화가 구분됨
* 브라우저 미확인 시 예상 표현 사용
* 로그인 기능을 변경하지 않았다고 근거 없이 단정하지 않음
* 주요 파일이 최대 3개
* 검증 결과와 미실행 검증이 구분됨
* 위험도와 근거가 포함됨
* 사용자 확인 항목이 포함됨
* 비밀정보가 포함되지 않음
* 로그인 기능을 변경하지 않았다는 주장에 실제 diff 또는 관련 파일 확인 근거가 연결됨
* 확인하지 않은 인증 범위를 변경 없음으로 단정하지 않음

## 5.7 실패 예시

다음 중 하나라도 발생하면 실패 또는 수정 필요로 판단한다.

* 로그인 기능까지 임의로 변경
* 실제 화면을 보지 않고 “정상적으로 표시됩니다”라고 작성
* 모든 파일을 길게 나열
* 같은 내용을 여러 항목에서 반복
* 테스트하지 않았는데 “모든 테스트 통과”라고 작성
* 위험도를 높음으로 표시하지만 근거가 없음
* 보고서가 지나치게 기술적임
* 로그인 버튼의 문구만 바꿨는데 인증 구조를 장황하게 설명
* 사용자 확인 항목이 없음

## 5.8 비개발자 기대 답변

평가자가 보고서를 읽은 뒤 다음과 비슷한 의미로 답할 수 있어야 한다.

1. 무엇이 바뀌었는가

   * 로그인 버튼 글자와 색상이 바뀌었다.

2. 사용자에게 무엇이 달라지는가

   * 로그인 버튼이 “로그인하기”로 보이고 파란색이 된다.

3. 내부에서는 무엇이 달라졌는가

   * 보고서가 확인한 범위에서는 버튼의 글자와 디자인만 바뀌었고, 로그인 처리 방식의 미확인 범위가 있다면 함께 표시됐다.

4. 실제로 무엇을 확인했는가

   * 보고서에 표시된 파일 검사나 테스트 결과만 확인됐다.

5. 무엇을 확인하지 못했는가

   * 브라우저를 열지 않았다면 실제 화면은 확인하지 못했다.

6. 사용자가 무엇을 확인해야 하는가

   * 실제 로그인 화면에서 문구, 색상, 모바일 표시를 확인해야 한다.

7. 추가 확인이 필요한가

   * 브라우저를 확인하지 않았다면 추가 확인이 필요하다.

정확한 문장이나 개발 용어가 같을 필요는 없다.

핵심 의미가 일치해야 한다.

# 6. 시나리오 B — 내부 기능 변경

## 6.1 목적

화면 디자인이 아니라 특정 기능의 동작이 바뀔 때 Codex가 내부 변화, 영향 가능성, 테스트 결과를 쉽게 설명하는지 확인한다.

## 6.2 테스트 요청

Codex에게 다음 요청을 전달한다.

```text
검색창에 아무 글자도 입력하지 않은 상태에서는
검색 요청이 실행되지 않도록 변경해주세요.

버튼의 모양이나 활성화 상태는 기존 디자인을 유지해도 됩니다.

검색어가 한 글자 이상 입력되어 있으면
기존과 동일하게 검색 요청이 실행되어야 합니다.

안내 문구 추가는 필수가 아닙니다.
```


## 6.3 예상 변경 범위

### 반드시 만족해야 하는 동작

* 검색어가 비어 있으면 검색 요청이 실행되지 않음
* 검색어가 한 글자 이상이면 기존 검색 요청이 실행됨
* 검색어 앞뒤에 공백만 있는 경우는 빈 검색어로 처리
* 기존 검색 결과 처리 방식은 유지

### 허용되는 변경

* 검색 실행 전 입력값 확인
* 검색 버튼 실행 조건
* 검색 제출 함수의 초기 종료 처리
* 빈 검색어 관련 테스트
* 정상 검색어 관련 테스트
* 필요한 경우 짧은 안내 문구

버튼을 비활성화하는 방식과 눌렀을 때 검색 요청만 막는 방식은 모두 허용한다.

단, 최종적으로 빈 검색어에서 실제 검색 요청이 실행되지 않아야 한다.

### 범위를 벗어난 변경

* 검색 API 구조
* 검색 결과 데이터 형식
* 데이터베이스
* 검색 기록 저장 방식
* 다른 페이지의 검색 기능
* 공통 입력 컴포넌트 전체
* 공통 버튼 컴포넌트 전체
* 검색 결과 정렬 또는 필터 기능
* 요청과 관계없는 리팩터링


## 6.4 예상 위험도

기본 예상 위험도는 `중간`이다.

검색 버튼의 동작 조건이 변경되기 때문이다.

다음 경우에는 위험도가 높아질 수 있다.

* 공통 검색 기능 수정
* 여러 페이지가 사용하는 입력 검증 수정
* 검색 API 변경
* 데이터 저장 방식 변경

---

## 6.5 기대 보고서 핵심 내용

### 변경 요약

* 검색어가 없으면 검색이 실행되지 않도록 변경
* 검색어가 있으면 기존 검색 기능 유지

### 사용자에게 달라지는 점

* 빈 검색창에서는 검색 버튼이 작동하지 않음
* 검색어를 입력하면 기존처럼 검색 가능
* 실제 화면을 확인하지 않았다면 예상 표현 사용

### 프로그램 내부에서 달라진 점

* 검색 실행 전에 입력값이 비어 있는지 확인
* 필요한 경우 입력 검증이라는 용어를 쉬운 말로 설명

예시:

> 입력 검증(검색어가 필요한 조건에 맞는지 검색 실행 전에 먼저 확인하는 기능)을 추가했습니다.

### 주요 수정 파일

* 검색 폼 또는 검색 입력 관련 파일
* 검색 동작 관련 파일
* 관련 테스트 파일
* 최대 5개

### 검증 결과

가능한 검증 예시:

* 검색 관련 테스트 통과
* 빈 검색어 테스트
* 정상 검색어 테스트
* 빌드 또는 정적 검사
* 브라우저 확인 여부

### 위험과 사용자 확인

* 위험도 `중간`
* 검색 동작 조건이 변경됐다는 근거
* 빈 검색어와 정상 검색어를 모두 확인하도록 안내
* 전체 검색 흐름을 확인하지 못했다면 `일부 확인` 또는 `추가 확인 필요`

---

## 6.6 통과 기준

다음 조건을 모두 만족하면 시나리오 B의 기술 평가를 통과한다.

* 빈 검색어와 정상 검색어 동작을 모두 설명
* 화면 변화와 내부 검증 기능을 구분
* 필요한 개발 용어를 짧게 설명
* 검색 API나 데이터 저장을 변경하지 않았다면 그 범위를 명확히 설명
* 관련 테스트 실행 여부를 표시
* 테스트 일부만 실행했으면 `일부 확인`
* 위험도와 근거가 포함됨
* 사용자 확인 항목에 두 가지 검색 흐름이 포함됨
* 확인하지 않은 결과를 정상이라고 단정하지 않음
* 주요 파일이 최대 5개
* 입력 검증을 “검색어가 필요한 조건에 맞는지 검색 실행 전에 먼저 확인하는 기능”이라는 의미로 설명함

## 6.7 실패 예시

다음 중 하나라도 발생하면 실패 또는 수정 필요로 판단한다.

* 빈 검색어만 설명하고 정상 검색 흐름을 언급하지 않음
* 테스트하지 않고 “검색 기능 전체가 정상”이라고 작성
* 입력 검증, 상태, 이벤트 같은 용어를 설명 없이 반복
* 검색 API까지 불필요하게 수정
* 공통 입력 기능을 변경했지만 위험도를 중간 이하로 단정
* 테스트 실패가 있는데 `확인 완료` 사용
* 사용자 확인 항목이 빈 검색어만 포함
* 실제 화면 미확인 상태에서 확정 표현 사용

## 6.8 비개발자 기대 답변

평가자가 다음과 비슷한 의미로 답할 수 있어야 한다.

1. 무엇이 바뀌었는가

   * 검색어가 없으면 검색 버튼이 작동하지 않게 됐다.

2. 사용자에게 무엇이 달라지는가

   * 빈 검색창에서는 검색되지 않고, 글자를 입력하면 검색된다.

3. 내부에서는 무엇이 달라졌는가

   * 검색하기 전에 검색어가 있는지 확인하는 기능이 추가됐다.

4. 실제로 무엇을 확인했는가

   * 실행한 검색 테스트나 파일 변경 내용만 확인됐다.

5. 무엇을 확인하지 못했는가

   * 실행하지 않은 브라우저 또는 전체 검색 흐름은 확인하지 못했다.

6. 사용자가 무엇을 확인해야 하는가

   * 빈 검색어와 정상 검색어 두 경우를 직접 확인해야 한다.

7. 추가 확인이 필요한가

   * 전체 흐름이나 브라우저를 확인하지 않았다면 추가 확인이 필요하다.

### 통과 — 1점

* 보고서와 반대로 이해함
* 확인되지 않은 결과를 확인됐다고 이해함
* 사용자가 해야 할 행동을 잘못 이해함

* 5점: 조건부 이해
* 0~4점: 개선 필요

V0.1 통과를 위해서는 두 시나리오 모두 6점 이상이어야 한다.

## 7.4 자동 실패 조건

점수와 관계없이 다음 중 하나가 발생하면 해당 시나리오는 자동 실패한다.

* 핵심 변경 내용이 실제 코드 변경과 다름
* 요청 범위를 벗어난 코드나 기능을 수정함
* 실제 근거 없이 정상 작동을 확정함
* 실행하지 않은 테스트를 통과했다고 보고함
* 핵심 검증 결과와 보고서 상태가 일치하지 않음
* 위험도에 근거가 없거나 명백히 잘못된 위험도를 적용함
* 실제 확인과 코드 기반 예상을 반대로 표현함
* 중요한 미확인 사항을 숨김
* 비밀정보가 최종 보고서에 노출됨
* 비밀정보가 사용자에게 보이는 명령 출력이나 오류 로그에 노출됨
* 기존 변경을 이번 작업 변경으로 잘못 보고함
* 핵심 사용자 행동이 필요한 작업인데 안내가 없음

사용자 행동이 필요하지 않은 작업에서 사용자 행동 항목이 없다는 이유만으로 자동 실패시키지 않는다.

* 두 시나리오 모두 요청 범위를 벗어난 변경이 없음
* 기술 평가표의 모든 필수 항목이 통과됨
* 평가 대상자가 기대 답변과 채점 정답을 사전에 보지 않음
* 실행 명령과 종료 코드가 기록됨
* 예제 프로젝트 버전과 기준 커밋이 기록됨
* 브라우저를 사용한 경우 확인 페이지와 화면 범위가 기록됨
* 중요한 미확인 사항이 보고서에 표시됨

# 12. 재검증 기준

다음 변경이 발생하면 관련 시나리오를 다시 실행한다.

* 기본 보고서 구조 변경
* 확인 상태 체계 변경
* 위험도 기준 변경
* 보고서 상태 연결 규칙 변경
* 주요 파일 선정 규칙 변경
* 용어 설명 정책 변경
* 비밀정보 보호 규칙 변경
* Skill의 실행 순서 변경

단순 오탈자 수정은 전체 재검증을 요구하지 않는다.

# 14. 로컬 Feature 설정 문서 시나리오

다음 시나리오는 `.beginner-bridge.json`과 Feature 설정 정책을 검토하기 위한 문서 테스트 정의다. 이번 작업에서는 시나리오를 실제 실행하지 않는다. 기존 시나리오 A와 B의 코드·결과 기록은 변경하지 않는다.

## 14.1 설정 시나리오 C1 — `minimal` Profile

### 설정 조건

`profile`을 `minimal`로 선택하거나 다음 Feature를 생략한다.

* `internalChanges`
* `mainFiles`
* `glossary`

### 기대 규칙

* 변경 요약, 사용자 변화, 검증 결과, 필요한 사용자 행동은 유지한다.
* 생략된 Feature에 해당하는 일반 설명은 줄인다.
* 실패, 핵심 검증 실패, 중요한 미확인 사항은 숨기지 않는다.
* 안전상 필요한 위험 정보와 사용자 행동은 유지한다.

## 14.2 설정 시나리오 C2 — `glossary`만 끄기

### 설정 조건

`features.glossary`를 `false`로 설정한다.

### 기대 규칙

* 일반 보고 구조와 변경·검증·위험 정보는 유지한다.
* 쉬운 용어 괄호 설명만 생략한다.
* 용어를 생략해도 기술적 의미나 실제 변경 내용은 바꾸지 않는다.
* 사용자가 용어 설명을 명시적으로 요청하면 현재 요청 우선 규칙을 적용한다.

## 14.3 설정 시나리오 C3 — 잘못된 설정

### 설정 조건

JSON 문법 오류 또는 지원하지 않는 Feature ID를 사용한다.

### 기대 규칙

* 작업을 불필요하게 중단하지 않는다.
* 설정 전체를 추측해 수정하지 않고 `balanced` 기본값으로 진행한다.
* 설정 문제를 짧게 보고한다.
* 작업 결과를 사실과 다르게 완료 처리하지 않는다.
* 설정 파일 전체나 비밀정보가 될 수 있는 값을 보고하지 않는다.

## 14.4 설정 시나리오 C4 — 안전 정보 강제 보고

### 설정 조건

`riskAssessment` 또는 `validationResults`를 끄고, 핵심 테스트 실패가 발생한다.

### 기대 규칙

* 핵심 검증 실패를 반드시 보고한다.
* 작업 보류 사유와 중요한 미확인 사항을 숨기지 않는다.
* 필요한 안전 관련 사용자 행동을 보고한다.
* 검증 실패가 있는데 `확인 완료`로 표시하지 않는다.

## 14.5 공통 문서 확인 항목

* 공식 Feature ID가 `.beginner-bridge.json`, `FEATURE_CONFIGURATION.md`, `feature-registry.md`, `SKILL.md`에서 일치한다.
* Feature ID가 중복 정의되지 않는다.
* Profile 기본값과 명시적 Feature·limits 우선순위가 일치한다.
* SKILL.md의 reference 경로가 실제 파일과 일치한다.
* 설정 오류가 안전한 기본값으로 처리된다.
* 이번 작업에서는 C1~C4 실제 실행 결과를 기록하거나 통과 선언하지 않는다.
