# jutell@2.0.0 — Release Showcase

What a real JuTell run actually looks like for `jutell@2.0.0`, in four parts: a real report, a real
failure, real observed overhead, and what this release does not prove. Every quote below is
condensed from an actual run (provider: OpenCode, connected via `jutell use opencode`) on a small
disposable test project — not rewritten for marketing, and not re-run to make the numbers look
better. Long internal tool logs, file paths, and session identifiers are left out; the words JuTell
actually said are not changed.

This file is the public, sanitized companion to this project's private dogfooding evidence. It is
meant to be small and easy to keep honest for future releases — see "Keeping this current" below.

## Report example

**Request:** "Change the login button text to 'Get Started'. Keep the function the same."

```text
Changed
- The login button text only, in one file (src/login.js). Button id and click handler unchanged.

Verified
- Re-read the edited file directly.
- Ran the existing test suite — 2/2 tests passed.

Risk — low
- Only the button text changed. Login handling was not touched.

Your next action
- Click the button once to confirm login still works.
```

The real report is longer than this (it also names the changed file in beginner terms, walks
through what/why/where, and defines two or three terms) — the excerpt above keeps the same claims
and the same order, just condensed for this page.

## Debug example

**Request:** "Block empty and whitespace-only searches. Show the result count."

The test fixture for this run already had one *unrelated* failing test before the request even
started — a pre-existing bug in a sort function this request never touches. JuTell's real,
unedited response:

```text
1 of 2 tests failed — an existing, unrelated sort-order bug, already broken before this
request started. It does not block this request: it's a different function this request
never touched.

Actually verified for this request: empty and whitespace-only searches are blocked, normal
search still works, result count displays correctly — each checked by running real code.

Nothing for you to do on this request. Open a new request only if you want the legacy sort
bug fixed.
```

JuTell did not call the whole task "failed" because of an unrelated pre-existing bug, and it did
not hide that the bug exists. It separated "your request: done and verified" from "something else
is still broken" — because those are different facts, and collapsing them either way would be
dishonest in a different direction.

## Efficiency snapshot

One bounded, single-sample comparison (n = 1) — not a benchmark suite:

| | Without JuTell | With JuTell |
|---|---|---|
| Observed tool actions | 8 | 13 |
| Provider-reported tokens (OpenCode, this run) | ≈ 63,700 | ≈ 160,400 |
| Result | 4-line summary | Structured, verified report |

JuTell's extra actions in this run were: one read of the project's `.jutell.json` config, one full
read of the JuTell Skill file, and one MCP call — three actions. The largest single driver of the
token difference was the full Skill-file read, which currently happens once per fresh agent
process rather than being cached or trimmed. That is an active area of investigation, not something
this release claims to have solved.

What the overhead buys, based on this same run: a grounded clarifying question instead of a guess
(see the README's "before work" example), an honest separation of verified vs. unrelated failure
(see "Debug example" above), and a structured report instead of a raw diff.

This was measured on OpenCode only. Codex's own token accounting was not captured for this
release — do not assume it matches.

## Known limits (this release)

- Small-change reports are still long (9–10 sections observed) even when a one-line summary would
  do; the report-length profile setting exists but wasn't observed shortening these cases.
- When a change can't be checked in a real browser, JuTell's report is honest about *what* wasn't
  checked, but doesn't yet use a single, explicitly-labeled "code-level vs. real-visual" field —
  the distinction currently lives in the wording, not a dedicated line.
- The efficiency numbers above are one OpenCode sample; no equivalent measurement exists yet for
  Codex or Claude Code.
- Ubuntu support is "limited testing" (see the platform table in the README) — Windows is the more
  thoroughly verified platform for the full command lifecycle.
